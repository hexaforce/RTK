# カバレッジ可視化 要件定義・設計ドキュメント（Draft）

車両がどこを・いつ計測したか（計測の網羅性・密度）を、**QuickSightのヒートマップ**で確認できるようにする機能。[路面値マップ配信 要件定義・設計ドキュメント.md](../路面値マップ配信/路面値マップ配信%20要件定義・設計ドキュメント.md)（道路値そのものを外部ツールへ配信する機能）とは目的もデータの流れも異なるため、別ドメインとして扱う。

------------------------------------------------------------------------

## 背景・スコープ

-   知りたいのは「道路の値」ではなく「**どこが計測済みで、どこが未計測か**」「計測密度がどれくらいか」
-   路面値マップ配信で行っている道路ネットワークへのマップマッチングは、カバレッジ可視化には**不要**。計測点（緯度経度＋計測時刻）をそのままQuickSightに渡せば、QuickSight組み込みのポイントマップ/ヒートマップビジュアルで表現できる（GeoJSONアップロードが要るレイヤードマップとは異なり、追加の地図データ作成が不要な機能）
-   閲覧はQuickSight（社内ダッシュボードとしての利用を想定）。外部ツールへの配信は対象外（そちらは路面値マップ配信のスコープ）

------------------------------------------------------------------------

## 全体アーキテクチャ

``` mermaid
flowchart LR
    COLLECT["計測データ収集<br/>(緯度経度+時刻の生データ)"]
    ATHENA["Athena<br/>(S3上の計測データを直接クエリ)"]
    QS["QuickSight<br/>データセット"]
    HEATMAP["ヒートマップ/<br/>ポイントマップビジュアル"]
    VIEWER["閲覧者<br/>(社内ダッシュボード)"]

    COLLECT --> ATHENA
    ATHENA --> QS
    QS --> HEATMAP
    HEATMAP --> VIEWER
```

-   路面値マップ配信のようなマップマッチング・バッチ集計処理は不要。計測データ収集が保存した生データを**Athena経由でQuickSightから直接参照**する軽量な構成
-   QuickSightの地理空間ビジュアル（ヒートマップ／ポイントマップ）が、緯度経度の密度を自動的に色の濃淡で表現してくれるため、道路セグメントへの変換なしでも「どこを走ったか」は十分に見える想定

------------------------------------------------------------------------

## 機能要件

| ID | 要件 |
|---|---|
| F-1 | 計測データ収集の生データ（緯度経度＋計測時刻）をQuickSightから参照できること |
| F-2 | 計測密度をヒートマップとして可視化できること |
| F-3 | 期間（直近N日、全期間など）でフィルタして表示できること |
| F-4 | 未計測エリア（データが存在しない箇所）が地図上で識別できること |
| F-5 | ダッシュボードへのアクセスを制御できること（[認証機能 要件定義・設計ドキュメント.md](../認証機能/認証機能%20要件定義・設計ドキュメント.md)のエンドユーザー（閲覧者）認証を参照） |

------------------------------------------------------------------------

## 非機能要件

| ID | 要件 | 備考 |
|---|---|---|
| N-1 | データ更新（新しい計測データの反映）が運用上妥当な頻度で行われること | QuickSightのデータセット更新スケジュール（SPICE）に依存 |
| N-2 | 計測データ量が増えてもダッシュボードの表示性能が大きく劣化しないこと | 生データを直接見るため、データ量次第では期間絞り込みや事前集計の検討が必要になる可能性 |

------------------------------------------------------------------------

## 未決事項

-   QuickSightのSPICE（インメモリキャッシュ）を使うか、Athenaへの直接クエリのままにするか（データ量・更新頻度・コストで判断）
-   計測データ量が非常に大きくなった場合、生データのままでは重くなる可能性がある。その場合はH3グリッド等での事前集計を挟むか検討（[路面値マップ配信 要件定義・設計ドキュメント.md](../路面値マップ配信/路面値マップ配信%20要件定義・設計ドキュメント.md)のマップマッチングとは別に、カバレッジ専用の軽量な集計を追加する可能性）
-   ダッシュボードの閲覧者（社内の誰が見るか）の範囲、QuickSightのユーザー管理・埋め込みの要否
-   「未計測」をどう判定するか（一定期間データがないエリアを未計測とみなす、等の閾値設計）

------------------------------------------------------------------------

## 次のステップ

1.  計測データ収集のデータ形式・保存先（S3のパス構造、Athenaテーブル定義）が固まり次第、QuickSightデータセットを試作
2.  ヒートマップ/ポイントマップビジュアルのPoC（実データでの見え方確認）
3.  データ量増加時の性能検証（SPICE利用の要否判断）
4.  閲覧者アクセス制御の方式を[認証機能](../認証機能/認証機能%20要件定義・設計ドキュメント.md)と合わせて確定
