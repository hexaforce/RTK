## 中継サーバの二重ロール

中継サーバは、接続してくる相手によって異なる役割を演じるプロキシとして機能する。

-   **車両（NTRIP Client）から見ると** → 中継サーバは **NTRIP
    Caster**（サーバ側）
-   **RTKプロバイダーから見ると** → 中継サーバは **NTRIP
    Client**（クライアント側）

``` mermaid
flowchart LR
    subgraph V["車両側"]
        VC["NTRIP Client"]
    end
    subgraph R["中継サーバ"]
        RS["NTRIP Caster役<br/>(車両向け)"]
        RC["NTRIP Client役<br/>(プロバイダー向け)"]
        RS <-->|"車両セッションと1:1で紐付け"| RC
    end
    subgraph P["RTK Provider"]
        PC["NTRIP Caster"]
    end

    VC <-->|"NTRIP (GGA/RTCM)<br/>車両認証"| RS
    RC <-->|"NTRIP (GGA/RTCM)<br/>プロバイダー認証"| PC
```

中継サーバはRTCM/GGAの中身を解釈・加工せず、**バイトストリームをそのまま透過**させることを基本方針とする。中身を解釈すると実装・保守コストとレイテンシが増える上、RTCMのバージョン差異等をプロバイダー選定前に気にする必要がなくなる。

## 通信シーケンス（詳細）

``` mermaid
sequenceDiagram
    participant VC as NTRIP Client(車両)
    participant RS as 中継サーバ
    participant SEC as Secrets Manager
    participant DB as 車両認証DB
    participant PC as RTK Provider

    VC->>RS: TLS接続 + NTRIP GET<br/>Authorization: Basic(車両APIキー)
    RS->>DB: 車両APIキー検証
    DB-->>RS: 有効 / 無効
    alt 無効
        RS-->>VC: 401 Unauthorized
    else 有効
        RS->>SEC: プロバイダー認証情報取得
        SEC-->>RS: Mountpoint/ID/PW
        RS->>PC: TLS接続 + NTRIP GET<br/>Authorization: Basic(provider credentials)
        PC-->>RS: ICY 200 OK
        RS-->>VC: ICY 200 OK
        loop 測位中
            VC->>RS: GGA
            RS->>PC: GGA (透過転送)
            PC-->>RS: RTCM
            RS-->>VC: RTCM (透過転送)
        end
    end
```

`車両認証DB`は[認証機能](../認証機能/認証機能%20要件定義・設計ドキュメント.md)が管理する`vehicle_credentials`テーブル（詳細は次節）。

## プロバイダー接続設定

RTK中継固有の`provider_id`属性・Secrets Managerのプロバイダー設定スキーマは、車両認証テーブル（`vehicle_credentials`）の説明とあわせて[認証機能 要件定義・設計ドキュメント.md](../認証機能/認証機能%20要件定義・設計ドキュメント.md)の「データストア」に記載している。

------------------------------------------------------------------------

## セッション・接続管理

-   車両1台につき、中継サーバ~プロバイダー間は**1本の永続TCPコネクション**を1:1で対応させる（車両セッション確立時にプロバイダー側セッションも確立）
-   車両側の瞬断（数秒〜数十秒）に対しては、プロバイダー側セッションを即座に切らず一定時間（例：30秒、要検討）保持し、再接続時の認証コストを削減する
-   プロバイダー側セッションが切断された場合は自動再接続を試みる（既存要件F-6）。再接続中は車両へRTCM欠落を許容するか、明示的なステータス通知を行うかは要検討
-   中継サーバのプロセス（ECS/Fargateタスク）単位でのセッション保持となるため、タスク再起動・スケールイン時のグレースフルシャットダウン（既存セッションのドレイン）を考慮する

## GGA送信間隔とVRS対応

-   VRS方式のプロバイダーでは、車両からのGGAに応じてプロバイダー側が仮想基準局を動的に生成・更新するため、**GGAの定期送信（一般的に1〜10秒間隔、プロバイダー仕様に依存）を継続することが前提**
-   中継サーバはGGAを解釈せず透過転送するだけでよいが、**GGA送信の途絶を検知するタイムアウト監視**は中継サーバ側で持つ（プロバイダーがセッションをタイムアウトさせる前に、車両側の異常として検知・アラート可能にするため）
-   直近のGGAをキャッシュしておき、一時的な途絶時に最終位置を保持する設計は、プロバイダー選定後に必要性を判断する（プロバイダー側のタイムアウト仕様次第）

------------------------------------------------------------------------

## データ形式・透過方針

-   **GGA**：NMEA-0183テキスト形式のまま中継（改変しない）
-   **RTCM**：RTCM 3.xバイナリストリームのまま中継（メッセージ種別の解釈はしない）
-   中継サーバはNTRIPのHTTPヘッダ部分（認証・Mountpoint選択等）のみをハンドリングし、ペイロード部分は完全にバイパスする

------------------------------------------------------------------------

## エラーハンドリング方針

| ケース | 中継サーバの挙動 |
|---|---|
| 車両認証失敗 | 401を車両へ返却、DBに失敗ログ記録 |
| プロバイダー認証失敗・Mountpoint不正 | 502相当のエラーを車両へ返却、運用アラート発報（プロバイダー側の設定ミスの可能性があるため） |
| プロバイダー側の輻輳・レート制限 | 指数バックオフで再接続、上限回数超過でアラート |
| プロバイダー側セッションタイムアウト | 自動再接続を試行、車両側へは可能な範囲で透過（再接続中はRTCM欠落） |

------------------------------------------------------------------------

## ログ・監査方針

-   記録する情報：接続開始/終了時刻、車両ID、送受信バイト数、切断理由
-   **GGA/RTCMの通信内容そのものは原則ログしない**（ストレージコスト・プライバシー配慮）
-   障害調査用に、車両ID指定で一時的にフル通信ログを取得できる「デバッグモード」を用意する（運用時の切り分けに有用）
-   ログ保存先はCloudWatch
    Logsを基本とし、長期保持・分析用途がある場合はKinesis Data
    Firehose経由でS3へアーカイブする

## 未決事項（本ドキュメント特有）

-   NTRIP v1/v2どちらをサポートするか（プロバイダー選定後に確定。v2の方がchunked
    transfer等モダンだが、プロバイダーの対応状況次第）
-   プロバイダーの契約単位（1台=1アカウントか等）が中継サーバのマッピングテーブル設計に与える影響
-   プロバイダー側セッションの瞬断許容時間の具体値
-   GGAタイムアウト監視のしきい値

## 次のステップ

1.  プロバイダー選定後、対応NTRIPバージョン・契約単位を確認し、本ドキュメントの未決事項を確定する
2.  Provider
    Adapterのインターフェース定義（Go/Rust/Node等、実装言語の選定を含む）
3.  PoC実装（1車両相当のトラフィックでの疎通確認、レイテンシ計測）

車両側APIキーの発行・失効フローの運用設計は[認証機能 要件定義・設計ドキュメント.md](../認証機能/認証機能%20要件定義・設計ドキュメント.md)側の未決事項として扱う。
