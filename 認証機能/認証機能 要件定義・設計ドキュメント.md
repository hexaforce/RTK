# 認証機能 要件定義・設計ドキュメント（Draft）

認証に関する共通基盤。3つのスコープを扱う。

1.  **車両（デバイス）認証**：[RTK中継](../RTK中継)、計測データ収集など、車両がバックエンドのAPIにアクセスするサービスで共通して利用する想定
2.  **バックエンド→外部サービス認証**：各サービスが外部の第三者サービス（RTKプロバイダー等）に接続する際の認証情報管理パターン
3.  **エンドユーザー（閲覧者）認証**：路面値マップ配信のように、車両ではなく人がダッシュボード/マップを閲覧するサービス向けの認証。車両認証（1）とは性質が異なるため別スコープとして扱う（詳細は下記「路面値マップ配信の閲覧者認証」）

------------------------------------------------------------------------

## 背景・スコープ

各サービスが個別に認証を実装すると、車両ごとの鍵の発行・失効オペレーションがサービスの数だけ分散し、運用が煩雑になる。そのため認証機能を共通基盤として切り出す。

現時点では[RTK中継サーバ向けに実装済みの車両認証](../RTK中継/RTK中継サーバ%20プロトコル・認証方式%20詳細設計.md)（APIキー方式、DynamoDB）が最初の実装であり、本ドキュメントはそこから汎用部分を抜き出したもの。計測データ収集は同じ車両認証（スコープ1）を再利用できる見込み。一方、路面値マップ配信は車両ではなく人がマップを見るサービスのため、車両認証の枠組みとは別に閲覧者認証（スコープ3）の検討が必要（いずれも未着手で、本ドキュメントを土台に設計する想定）。

------------------------------------------------------------------------

## 認証方式の選定

| 方式 | 概要 | メリット | デメリット |
|---|---|---|---|
| **APIキー方式（案A）** | 車両ごとに発行したAPIキーをHTTP標準のBasic認証枠（またはヘッダー）に格納 | 実装コストが低い、既存クライアント実装のままでも移行しやすい | 漏洩リスク（キー流出時はローテーションで対応） |
| **mTLS方式（案B）** | 車両ごとにクライアント証明書を発行し、TLSハンドシェイクで認証 | なりすまし耐性が高い | 証明書のプロビジョニング・失効管理(CRL/OCSP)の運用負荷 |

**推奨：初期フェーズはAPIキー方式（案A）を採用する。**
理由は、既存のRTK中継サーバ向けNTRIP
Client実装（車載側）がBasic認証に標準対応しており、車載チームへの追加要求が少ないため。台数増加やセキュリティ要件の厳格化に応じて、mTLSまたはAPIキー+デバイス証明書の併用へ移行する。

## データストア

車両認証はDynamoDB、RTKプロバイダーの接続情報はSecrets Managerで管理する。役割が異なるため保存先を分けている（前者は「誰が接続してよいか」、後者は「どこに繋ぐか」）。

### DynamoDB（`vehicle_credentials`テーブル）

| 属性 | 説明 | 管轄 |
|---|---|---|
| `vehicle_id`（パーティションキー） | 車両を一意に識別するID | 共通 |
| `api_key_hash` | 車両が提示するAPIキーのSHA-256 hex（平文は保存しない） | 共通 |
| `provider_id` | この車両が使うRTKプロバイダーのアカウントを指す値。Secrets Managerの`rtk-relay/providers/<provider_id>`に対応する | RTK中継が追加 |

-   キーはハッシュ化して保存し、レインボーテーブル攻撃を防ぐ
-   `vehicle_id`/`api_key_hash`が全サービス共通の基盤属性。利用サービスごとに固有の属性をこのテーブルに追加する形で拡張できる（サービスごとに別テーブルを作る必要はない）。`provider_id`はRTK中継がこの仕組みで追加した最初の例
-   計測データ収集・路面値マップ配信で必要になる属性は、それぞれの設計時にこのテーブルへの追加を検討する

`provider_id`の単位には注意が必要：多くのRTKプロバイダーは「1アカウント=同時接続1台まで」という契約になっている（[RTKプロバイダー比較検討資料（Draft）.md](../RTK中継/RTKプロバイダー比較検討資料（Draft）.md)の「車両台数が多い場合のコスト構造」参照。例外はKDDIのPPP-RTKメニューのみ）。したがって`provider_id`は「プロバイダー会社名」（`docomo`）ではなく「**個別の契約アカウント**」（`docomo-vehicle-001`）を指す単位で運用する。台数課金型プロバイダー以外では、車両1台につきプロバイダー契約1件・Secrets Managerシークレット1件が対応することになる。

### Secrets Manager（RTKプロバイダーの接続情報）

`provider_id`の解決は、下記「バックエンド→外部サービス認証」のパターンに沿う（シークレット名`rtk-relay/providers/<provider_id>`）。

#### プロバイダー設定スキーマ

各社RTKプロバイダーはID/Passwordだけでなく、[RTKプロバイダー比較検討資料（Draft）.md](../RTK中継/RTKプロバイダー比較検討資料（Draft）.md)の調査で分かった通り、NTRIPバージョンや暗号化ポートの有無など接続時の付随パラメータが異なる。これを吸収するため、プロバイダー設定（Secrets
Managerの値）は以下のJSONスキーマとする（`internal/providerconfig.Provider`）。

``` json
{
  "host": "string (必須)",
  "port": "string (必須)",
  "mountpoint": "string (必須)",
  "username": "string (必須)",
  "password": "string (必須)",
  "ntrip_version": "\"1\" | \"2\" (省略時 \"2\")",
  "tls": "bool (省略時 false。docomoの2102ポートのようなTLS提供プロバイダー向け)",
  "gga_interval_seconds": "number (省略可。プロバイダー推奨のGGA送信間隔、参考値)",
  "extra_headers": "object (省略可。上記で表現しきれない任意のNTRIPリクエストヘッダー。例: アカウント/契約IDをヘッダーで要求するプロバイダー向け)"
}
```

`host`/`port`/`mountpoint`/`username`/`password`は調査した全社が共通して必要とする最小集合。それ以外はプロバイダーごとに有無が分かれるため、`extra_headers`を汎用の逃げ道として用意し、未知のプロバイダー要件にもコード変更なしで対応できるようにしてある。このスキーマはRTK中継固有（NTRIP前提）であり、他サービスが外部サービス認証パターンを採用する場合はそれぞれ独自のスキーマを持ってよい。

## バックエンド→外部サービス認証

車両認証（上記）とは別に、バックエンドの各サービス自身が外部の第三者サービス（RTKプロバイダー等）に接続するための認証情報管理にも、共通のパターンを適用する。

-   **1外部アカウント = 1 Secrets Managerシークレット**を原則とする
-   シークレット名は`<サービスプレフィックス>/<account_id>`という命名規則にする（例：RTK中継の場合`rtk-relay/providers/<provider_id>`）
-   利用サービスのIAMタスクロールには、このプレフィックス配下への`GetSecretValue`のみをワイルドカードで許可する。これにより**新しいアカウントの追加はシークレットを1個作るだけで完結し、Terraformの変更もコードの変更も不要**になる
-   接続確立のたびに都度Secrets Managerを引く設計にする（起動時に1回だけ読み込む方式にしない）ことで、アカウントの追加・切替に再デプロイが不要になる
-   現状の実装：RTK中継が`rtk-relay/providers/<provider_id>`という命名でこのパターンを採用している（詳細は上記「データストア」の`provider_id`属性を参照）
-   計測データ収集・路面値マップ配信が外部サービス（地図タイル配信API等）と連携する際も、同じパターンの採用を検討する

## 路面値マップ配信の閲覧者認証

路面値マップ配信は車両ではなく**人**がマップ/ダッシュボードを閲覧するサービスであるため、車両認証（APIキー方式）ではなく別の認証が必要になる。マップエンジンはAWSのサービス（候補：QuickSight）を想定しているが未確定。

QuickSightのような閲覧系AWSサービスを使う場合、認証は2層に分かれる想定。

1.  **バックエンドがQuickSight
    APIを呼び出すための認証**：バックエンド用のIAMロールに`quicksight:GenerateEmbedUrlForRegisteredUser`等の権限を付与する形になる見込み。これは性質上「バックエンド→外部サービス認証」（上記スコープ2）のAWS版
2.  **誰がそのマップを見てよいかの認証（閲覧者本人の認証）**：QuickSightのユーザー管理（IAM Identity
    Center連携など）に寄せるか、埋め込み(embedding)であればアプリ側が発行するセッションで閲覧者を識別してから埋め込みURLを発行するか、方式は未定

マップエンジンの選定自体が未確定のため、本セクションは選定後に具体化する。

## 未決事項

-   mTLSへの移行タイミング・トリガー
-   複数サービス共通のAPIキー発行・失効の運用フロー（誰が、どのツール/手順で発行するか）
-   サービスごとに認証テーブルを分けるべきか、共通テーブルへ属性を追加し続けるべきかの判断基準（属性が増えすぎた場合の設計限界）
-   計測データ収集・路面値マップ配信それぞれで、この認証機能をどう呼び出すか（API Gateway等で共通化するか、各サービスが個別にDynamoDBを引くか）
-   バックエンド→外部サービス認証のパターンを、RTK中継以外（計測データ収集・路面値マップ配信）が実際に採用するかどうかは、各サービスの外部連携要件が固まってから判断する
-   路面値マップ配信のマップエンジン自体が未選定（候補：QuickSight）。選定後、閲覧者認証の具体的な方式（QuickSightユーザー管理／IAM Identity Center連携／埋め込みセッション認証等）を確定する
