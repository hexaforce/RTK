# 路面値マップ配信 要件定義・設計ドキュメント（Draft）

計測データ収集が集めた計測データから**道路値マップデータ**（道路セグメント単位の集計値）を作成し、**自社以外のMapEngineを用いたツール**（社内外の別アプリ、パートナーのマップ製品等）へ配信する機能。可視化そのもの（QuickSightでの表示）は対象外で、そちらは[カバレッジ可視化 要件定義・設計ドキュメント.md](../カバレッジ可視化/カバレッジ可視化%20要件定義・設計ドキュメント.md)を参照。本ドキュメントは「データを作って渡すところまで」がスコープ。

------------------------------------------------------------------------

## 背景・スコープ

-   計測データ（車両の位置＋路面値）は緯度経度の点データとして集まる。これをそのまま配信しても、他のMapEngineツール側で「どの道路の値か」を解釈できない
-   H3グリッド集計は道路形状を認識できず、道路のマッチング精度に問題がある（詳細は検討の経緯を参照）ため、**道路ネットワーク（OSM）へのマップマッチング**を採用する
-   配信先はQuickSightのような自社BIダッシュボードではなく、**外部のMapEngine（MapLibre GL JS等）を使う別のツール/アプリ**を想定する。したがって配信されるデータは「表示済みの画面」ではなく「地図データそのもの（GeoJSON/ベクタータイル等）」になる

------------------------------------------------------------------------

## 全体アーキテクチャ

``` mermaid
flowchart LR
    COLLECT["計測データ収集<br/>(緯度経度+路面値+時刻)"]
    OSM["道路ネットワークデータ<br/>(OSM, AWS Open Data経由でAthenaから参照)"]
    MATCH["マップマッチング<br/>バッチ処理<br/>(エンジン未定: OSRM/Valhalla/FMM等)"]
    AGG["道路セグメント単位<br/>集計処理"]
    STORE["道路値マップデータ<br/>(S3: GeoJSON / PMTiles等)"]
    DIST["配信<br/>(S3 + CloudFront)"]
    EXT["外部MapEngineツール<br/>(MapLibre GL JS等を使う<br/>社内外の別アプリ)"]

    COLLECT --> MATCH
    OSM --> MATCH
    MATCH --> AGG
    AGG --> STORE
    STORE --> DIST
    DIST -->|"GeoJSON / ベクタータイル配信"| EXT
```

-   **マップマッチング〜集計はバッチ処理**（走行中のリアルタイム処理ではない）。計測データが溜まったタイミング、または定期スケジュールで実行する想定
-   **道路ネットワークデータ**はAWS Open Data Registry上のOSMデータ（`s3://osm-pds/`、またはDaylight OSM DistributionのParquet）をAthenaから直接参照する。自前でOSMをホスティング・変換する必要はない
-   **配信フォーマット**は外部ツール側の実装に依存する。GeoJSON（シンプルだが大きいデータには不向き）か、ベクタータイル（PMTiles等、S3+CloudFrontから直接配信可能で大規模データに強い）のどちらかを、配信先の要件に応じて選ぶ

------------------------------------------------------------------------

## 機能要件

| ID | 要件 |
|---|---|
| F-1 | 計測データ収集からの計測点を取得できること |
| F-2 | 計測点を道路ネットワーク（OSM）にマップマッチングできること |
| F-3 | 道路セグメント単位で計測値を集計できること（平均値・最新値・N日以内の値など、集計方法は要件次第） |
| F-4 | 集計結果を外部MapEngineツールが読み込める形式（GeoJSONまたはベクタータイル）で出力できること |
| F-5 | 出力データをS3等から配信でき、配信先（外部ツール）から継続的に参照できること |
| F-6 | データ更新時に配信内容を更新できること（更新頻度は要件次第） |
| F-7 | 配信データへのアクセスを制御できること（[認証機能 要件定義・設計ドキュメント.md](../認証機能/認証機能%20要件定義・設計ドキュメント.md)のバックエンド→外部サービス認証/エンドユーザー認証パターンを参照） |

------------------------------------------------------------------------

## 非機能要件

| ID | 要件 | 備考 |
|---|---|---|
| N-1 | マップマッチング処理が計測データ量の増加に対してスケールすること | バッチ処理なので即応性より処理完了時間が重要 |
| N-2 | 配信データのサイズが外部ツール側で扱いやすい範囲に収まること | GeoJSON採用時は特に注意（大規模データはベクタータイル化を検討） |
| N-3 | 道路ネットワークデータ（OSM）の更新に追従できること | 週次〜月次程度の同期で十分と想定 |

------------------------------------------------------------------------

## 未決事項

-   **マップマッチングエンジンの選定**：自前ホスト（OSRM / Valhalla / GraphHopper / FMM）か、マネージドAPI（Mapbox / Google Roads API / HERE / TomTom）か。コストと運用負荷のトレードオフで判断する
-   **集計ロジック**：道路セグメントの値をどう集計するか（単純平均、直近N件の平均、外れ値除去の要否など）
-   **配信フォーマット**：GeoJSONで十分か、ベクタータイル化（Tippecanoe等でMVT/PMTiles生成）が必要か。データ量・更新頻度次第
-   **配信先の外部MapEngineツールの仕様**：具体的にどのツール/アプリが消費するか、要求されるデータ形式・更新頻度がまだ不明
-   **更新頻度**：バッチ処理をどの頻度で回すか（日次、計測データ到着トリガー等）
-   **道路セグメントのID管理**：OSMのway IDをそのまま使うか、自社独自のセグメントIDを振るか（前者はOSM編集で分割/統合されるリスク、後者は変換・管理コストが発生）
